**Answers (2026-10-20, P5, decided autonomously):** P5 has no M-items; these choices fill gaps and are recorded here.
- **No `CLOUDINARY_URL` yet:** `CloudinaryStore` is "not configured" when the variable is blank: the PDF is not kept (log `pdf storage skipped: not configured`), the submission still proceeds with its text, `pdfStored` is `false`, and a later PDF-link request (P10) gets "not available". A malformed URL stops startup without echoing it. V-10 stays pending secrets.
- **AES key:** `TEXT_AES_KEY_BASE64` is required; a missing, non-Base64 or non-32-byte key stops startup with a message that never contains the key. `key_version` = 1.
- **Typed contact details are encrypted too:** the optional sender email, phone and UPI ID are stored only inside `contacts_cipher` (AES-GCM JSON, AAD = `<submissionId>:contacts`), not as the PRD's plain columns. `sender_domain` (D-33.6: typed email, else the first email address in the letter) is computed at upload and stored in clear.
- **`submission.created` carries IDs and metadata only** (no sender email, phone or UPI ID, unlike the earlier 02 §5 draft, now updated). The consumer loads text and contacts with `SubmissionService.findContent(submissionId)`.
- **Idempotency-Key:** required, 8–100 characters of `A–Z a–z 0–9 - _ . :`, compared case-sensitively (`ascii_bin`), unique per owner. "Same content" = same source type, same file bytes or text, and the same optional fields (`request_sha256`); otherwise 422 `IDEMPOTENCY_KEY_REUSED`. A replay is answered before the upload limit and without re-validation.
- **Upload limit (D-12):** counted from `submission` rows (5 per 10 minutes), 429 `UPLOAD_LIMIT` with `Retry-After`. Checked before the slow steps (cheap rejection) and again inside the short insert transaction, so parallel uploads can overshoot only within milliseconds (a soft limit; Bucket4j still caps bursts). A PDF already stored for a refused upload is deleted.
- **Status codes:** 413 `FILE_TOO_LARGE` (> 5 MB, also from the servlet multipart limit), 415 `UNSUPPORTED_FILE_TYPE` (Tika magic bytes), 422 `TOO_MANY_PAGES` / `PDF_ENCRYPTED` (any encryption, including owner-password-only) / `PDF_UNREADABLE` / `PDF_TIMEOUT` / `PDF_TOO_COMPLEX` (decompression budget) / `TEXT_TOO_SHORT` (< 50 non-space characters → "paste the text instead") / `TEXT_TOO_LONG` (PDF text over 50,000 characters), 400 for a missing/invalid key, file **and** text or neither, and pasted text over 20,000 characters (`VALIDATION_FAILED`), 503 `STORAGE_UNAVAILABLE` (Cloudinary) or `SERVER_BUSY` (PDF pool full).
- **Who:** `POST /api/submissions` needs role USER (PRD §11); reads are owner-scoped for any signed-in user. The list returns the newest 100, without DELETED rows.
- **Sweeper timeline (D-28):** re-publishes at about 2, 6, 14 and 30 minutes after upload (waits 2/4/8/16), then FAILED once the 4th re-publish is 16 minutes old (≈ 46 minutes). Each re-publish is counted (compare-and-set) before it is sent after that commit; if Kafka refuses a send, the rest of that run waits for the next minute.
- **Producer limits:** `acks=all`, idempotence on, `max.block.ms` 5 s, `delivery.timeout.ms` 15 s; the publisher waits at most 20 s and never fails the 202.
- **Uploads stay in memory** (`file-size-threshold` 6 MB), so letters are never written to a temp file.
- **Publishing after commit, without a `@TransactionalEventListener`** (differs from the 04 P5-05 file note): the upload and the sweeper each save in their own short `REQUIRES_NEW` transaction and call `SubmissionEventPublisher.publish` after it returns. An `AFTER_COMMIT` listener runs before Spring releases the JDBC connection, so a slow or down broker would have held a pool connection for up to 20 s per upload (found in the P5 review).
- **PDF public ID** = `submissions/` + sha256(owner:idempotencyKey:requestSha256) (04 P5-04 said owner:key). Byte-identical retries still share one asset, but a racing request that reuses the key for another file can no longer overwrite the saved submission's PDF; the loser's own asset is deleted.
- **PDF bomb limit (PRD §14.4 "memory limit"):** PDFBox 3 decompresses streams into unbounded heap buffers and has no setting for it, so at startup `PdfDecodeBudget` wraps each PDFBox decoder once; during an extraction it stops at 16 MB per stream, 64 MB per file or the 10 s deadline → 422 `PDF_TOO_COMPLEX` (other threads are unaffected). The page's own fast Flate path is pre-decoded through the same budget. If a PDFBox upgrade breaks the wrapping, startup fails instead of reading PDFs unprotected. Extracted text is capped at 50,000 characters (`TEXT_TOO_LONG`).
- **Sender-domain extraction (D-33.6)** uses flat, bounded regex classes plus a Java check of the labels: the first version could take seconds on 20,000 characters without an `@` and overflow the regex stack on thousands of dotted labels (found in the P5 review; now a test).
- **Done (coordinator): Caddyfile** has `request_body { max_size 6MB }` on `/api/submissions` so very large uploads are refused at the edge (the app already returns 413; not changed in P5 because the Caddyfile was out of scope).

**Answers (2026-10-20, P6, decided autonomously):** M-06 → the recommended default, Guava `InternetDomainName.topPrivateDomain()` (Guava 33.7.2-jre, its bundled public suffix list). The other choices fill gaps:
- **SSRF guard (`DomainValidator`):** a domain passes only if it is ≤ 253 characters of letters, digits, dots and hyphens (so brackets, colons, ports, paths, schemes, `@`, `%` and spaces fail), converts with `IDN.toASCII` (STD3), has ≥ 2 valid labels, an alphabetic or punycode top-level label (so every IPv4 spelling fails), is not under a local or special-use name (`.localhost .local .internal .localdomain .lan .home .corp .intranet .arpa .invalid .test .example .onion .alt`), and sits under a public suffix without being one. RDAP asks for the registry-level name (`topDomainUnderRegistrySuffix()`, which differs from M-06 only under private suffixes such as `x.github.io`). The report keeps the sender domain only when it passed the guard, so an IP literal can never become a registry marker later. A typed `x@[::1]` is already refused by the upload's `@Email` check (400).
- **C5/C6 are not run (NOT_APPLICABLE, no lookup)** when there is no sender domain, when it fails the guard, or when it is a free-mail provider (C2 covers that; the provider's domain age or DNS says nothing about the employer).
- **RDAP:** servers only from the IANA bootstrap file (cached 24 h, at most 1 MB), HTTPS only (`offershield.lookup.rdap.require-https`, switched off only by the local tests' HTTP stub); at most 2 redirects, each only to a bootstrap server; one 5 s deadline per lookup; answers ≤ 256 KB; a found date (or an answer without one) cached 24 h, failures not cached. No registration event (NIXI, I-29) or a date in the future → C5 UNAVAILABLE.
- **DNS (dnsjava):** asks the system's resolvers (configurable `offershield.lookup.dns.servers`), never connects to the domain. MX at the sender host (a null MX "." counts as none); DMARC = TXT starting `v=DMARC1` at `_dmarc.<host>`, else at `_dmarc.<registrable domain>` (RFC 7489). One 3 s budget per lookup; NXDOMAIN = no record; SERVFAIL/timeout → C6 UNAVAILABLE; results cached 1 h. C6 is one signal: no MX +15, no DMARC +5.
- **C1 and D-09:** the "no fee" rule is applied **per clause** (split at sentence ends, `; , ! ?`, blank lines and "but/however/lekin"; a single line break does not split, because PDF text breaks lines mid-sentence; dots and commas inside numbers, email addresses and "Rs." do not split). "An amount" = a number with ₹/Rs/INR/rupees/"/-", or a grouped number like 5,000 (a bare "3" or a year is not an amount); a zero amount ("₹0") counts as a negation. Money the employer pays ("we will pay ₹50,000 as a joining bonus") is not a request. C1 adds 0 points and sets `hardOverride`; the score stays the sum of the other points, and the report says `hardOverride: true`.
- **C2** source kind 1 (the address is in the letter; the free-mail list is the curated input). An offer letter always claims an employer, so the sender domain alone decides.
- **C8** "company channel" = any email address (typed or in the letter) on a domain that is not a free-mail provider.
- **C9** counts distinct phrases (case and spacing ignored), at most 2; the list includes Hinglish words (M-08 note).
- **Evidence** is the triggering clause (or phrase list), whitespace collapsed, with emails, UPI IDs and phone numbers masked (`[email]`, `[UPI ID]`, `[phone]`), at most 200 characters. It travels in `analysis.completed`, so no contact detail leaves the database through Kafka.
- **A check that throws** becomes UNAVAILABLE ("could not run this time"), logged with the check code and exception class only; the report still arrives (PARTIAL).
- **Tables:** `report` (V10) and `report_signal` (V11; `SIGNAL` is a reserved word in MySQL). The PRD's `evidence_json` is a single `evidence VARCHAR(200)` (02 §5 has one evidence string per signal); `source_kind` is an INT 1–5; one row per check per report (UNIQUE `report_id, check_code`); `report.id` = submission ID (FK); `hard_override` added.
- **Consumers:** `ErrorHandlingDeserializer` → `JacksonJsonDeserializer`, type headers ignored, each `@KafkaListener` names the one event class it reads, trusted package `com.offershield.common.events`; `auto-offset-reset: earliest` (a new group misses nothing), ack mode `record`, `max.poll.records=1` for `analysis`. Error handler: 3 retries at 1/2/4 s, then `<topic>.DLT` on the same partition (explicit resolver); malformed JSON, wrong type and `InvalidEventException` (no IDs, unknown outcome) go there at once. A record that failed to deserialize is dead-lettered with its original bytes. D-27: the DLT records keep the exception class headers but not the exception message or stack trace; Spring's own retry/recovery logging is at DEBUG; one WARN line per dead-lettered record (topic, partition, offset, exception class) with the record's request ID.
- **Request ID:** a `RecordInterceptor` copies the `requestId` header (only if it is a UUID) and the record key (submission ID) into the MDC, so the upload, the analysis and the status update share one request ID; the analysis also sets the owner's user ID.
- **Duplicates and the re-send fix (D-28):** the analysis checks `processed_event` before any work; a duplicate with a stored report re-sends `analysis.completed` built from that report (same deterministic event ID). The report is saved in one short transaction with `INSERT IGNORE` into `processed_event`; the lookups run before it, outside any transaction. If the broker does not confirm the completion, the listener throws, the record is retried, and the retry takes the re-send path (the sweeper is the last resort). The analysis uses the owner and college stored with the submission, not the IDs in the event.
- **Status consumer:** QUEUED → READY/PARTIAL, and also **FAILED → READY/PARTIAL** when a completion arrives after the sweeper gave up (for example after a long broker outage), because the report exists and is worth showing; READY, PARTIAL and DELETED rows never change (02 §7 updated).

Generic greetings ("Dear Candidate", "Sir/Madam", "Team") stay. Placeholder look-alikes in the letter are neutralised to round brackets; zero-width characters are removed. The map back never leaves the JVM. Text: control characters removed, spaces collapsed, at most one blank line, then masked, then capped at 6,000 characters.
